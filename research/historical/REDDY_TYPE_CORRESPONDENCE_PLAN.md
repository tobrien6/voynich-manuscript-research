# Positional H / Reddy type-correspondence plan, version 1

Question: do the nominally matching source records preserve the equality
partition of token positions, and therefore immediate-repeat measurements,
across the two supplied notations? Freeze and publish this plan and a
synthetic-tested producer before measuring the cross-notation type graph.

This follow-up depends on the published literal-envelope audit in PR #175.
The full source material, parent inventories, all envelope/order/count results
and historical approximate repetition results are exposed. This is a
descriptive partition diagnostic, not untouched evaluation or a fitted
alphabet conversion. It does not propose a decipherment.

## Fixed inputs and conditional positional pairing

Pin fifteen source/reader/plan/report dependencies, including the original
eleven source dependencies and the complete #175 human/machine plan, producer
and report. Verify all dependency bytes, the six local Reddy references, and
complete parent-envelope report replay before new analysis. Execute no author
program and publish no raw corpus or author payload.

Reuse every native H record, the empty-special-code (fallback-retained)
accepted normalization, and the unchanged full Reddy annotated whitespace
tokens. Apply no manual exclusion, code deletion, case folding, punctuation
deletion, uncertainty filter, alphabet mapping or body repair.

Pair a token position only by exact literal shared four-field record key and
the same within-record token index. Require equal token counts and unchanged
shared-key source order. Retain all unmatched/empty source identities through
the complete pinned parent ledger; fail if an unmatched record contains tokens.
Equal envelope/count/order evidence supports this nominal positional
comparison, but does not prove that the paired tokens correspond to physical
words or glyphs. Do not choose a different alignment to improve agreement.

## Equality partition and complete graph

Within each source, token type means exact equality of its original notation
strings. Give each type a SHA-256 ID of its UTF-8 token bytes, with separate H
and Reddy domains; verify no within-domain hash collision. Do not compare
notation spellings across the two domains or publish raw token strings.

Build the full bipartite type graph under the fixed positional pairing. Retain
every type-pair edge, occurrence count and supporting `(selected H ordinal,
local token index)` position. Record all type frequencies and degrees in both
directions, notation lengths and asterisk presence. Retain all one-to-many and
many-to-one classes; neither ambiguity nor asterisks trigger exclusions.
Account for the full population, every edge and every position exactly once.

Also count every unordered pair of distinct paired positions: equality in both
notations is `sum choose(edge_count, 2)`; equality in each domain separately is
`sum choose(type_frequency, 2)`. Retain H-only/Reddy-only equality and neither
equality counts with the full `choose(paired_positions, 2)` denominator. These
exact contingency identities provide a second partition check, without a
misleading agreement score dominated by unequal pairs.

Report whether each direction is functional (every source type has one target)
and whether the complete position equality partitions are identical (all
degrees are one in both domains). Functional/nonfunctional describes this
exposed finite positional relation; it supplies no general conversion rule or
out-of-sample success claim. Preserve every outcome, not only simple classes.

## Immediate-repeat consequences

Flatten the paired records in native H source order. For both original token
streams, compute A (equal neighboring occurrence edges) and B (distinct types
that have at least one equal neighbor). Include native-record joining edges;
do not add cyclic edges. Retain the full two-by-two equality-event counts,
within-record/joining breakdown, and every edge whose equality differs between
notations, with source record/local-index descriptors for both endpoints.
Record joining boundaries even when no event differs. Preserve all types,
including singleton/asterisk notation, and use no random control or tail.
Report B separately for within-record and joining edges, plus their repeated
type overlap. Identify every intervening selected-H ordinal at a flattened
join. No manual exclusions or removed token positions occur in this stream;
empty record boundaries remain in the parent ledger. A flattened join is a
declared file-stream edge, not verified physical adjacency.

Identical equality partitions imply identical immediate-repeat edge flags and
A/B counts on these paired positions. Equal A/B totals alone do not imply
partition identity. Test both facts synthetically, including equal totals with
different repeated types or discordant edges. Do not infer a transcription
mapping, language or mechanism from either agreement or disagreement.

## Validation and rights

Before new source measurements, test bijective relabeling, functional merges,
splits in the opposite direction, nonfunctional relations, repeated-event
discordance within records and at joins, singleton/empty cases, asterisks,
non-ASCII hash transport, exact support accounting, source order/count failures,
hash collisions, dependency/parent mismatch and output failure preservation.
Protect every pinned source, both plans/producers and all six local reference
files against direct/symlink/hardlink output aliases before computation and
after serialization, including aliases introduced during computation.

Native H credit/reuse terms remain explicit. Reddy's pinned tree has no found
license; its raw bodies/token strings and author source remain local. Publish
original audit code, source metadata, type IDs and complete support positions.
Keep this comparison separate from modern H/IT2a lossy projections, statistical
null calibrations and any future frozen glyph/notation conversion candidate.
